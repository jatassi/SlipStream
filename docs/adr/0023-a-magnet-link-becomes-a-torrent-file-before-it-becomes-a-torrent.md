# A magnet link becomes a .torrent file before it becomes a Torrent

A Grab of a magnet link gets the torrent's metadata in its Fetching stage, before any Torrent exists. Fetching keeps its meaning, "get the .torrent", and gains a second source: the swarm, through the Downloading Node the fetch routes to. That Node runs a metadata search, which is a metadata-only engine torrent outside the plan, and the Controller composes the .torrent from the magnet link's trackers and the info dictionary a peer sent. The composed .torrent goes through the same checks as one an Indexer serves, so a Torrent's `metainfo` stays `NOT NULL` and every reader of name, size, private, trackers, files and progress keeps its preconditions. The Node answers the info dictionary only after the metadata-only torrent is removed, so a hash is in a Node's engine at most once. The download is then a fresh add from the composed metainfo with a new peer ID. One function on the Node, `mayDiscover`, is the privacy rule for both add paths: a torrent with metadata uses DHT and PEX if it isn't private, and a metadata search uses them if its magnet link names no tracker. LSD stays off for all. Decided in the magnet links design, decisions 1, 2, 10, 11 and 14.

## Considered Options

- **A Torrent with a nullable metainfo, filled in by a Node report.** Rejected. The magnet would be a Torrent at once, visible and controllable on the Torrents page with one engine torrent from first contact to completion. But every reader of a Torrent would need a "before metadata" case, and the schema, `Attach`, the reports, `TorrentResponse`, the plan and the faults would each gain one. A libtorrent seeder never serves a private torrent's metadata, so the common magnet failure is a private one, and in that shape it would leave a failed Torrent the Admin must remove by hand.
- **Keeping the metadata-only engine torrent for the download.** Rejected. libtorrent can't set baseline totals after an add, the search's file priorities are all 0 and would need resetting, and the shim already merges a re-add of a parting torrent into the existing handle with the wrong parameters. Its one benefit was to avoid a private tracker's per-peer window, and a fresh add has a new peer ID, so UNIT3D's window and duplicate rule don't hold it.
- **Resolving on the Searching Node.** Rejected. A Searching Node has no engine, and the search would announce from a Node other than the one that downloads, with that Node's DHT setting and peers.
- **DHT for every magnet link before its metadata arrives.** Rejected. A magnet link carries no private flag, so DHT before metadata would send a private tracker's info hash to the public DHT. Only a magnet link that names no tracker uses DHT before metadata.

## Consequences

- A public magnet link that names only trackers that are down never resolves, because DHT before metadata is only for a magnet link with no tracker. This is the price of never leaking a private tracker's info hash.
- A private magnet link announces its passkey for the whole metadata wait, because libtorrent peers never serve a private torrent's metadata. The wait is the global `downloading.metadataWait` setting, 30 minutes by default. When it passes, the Grab fails at Fetching with `no_metadata` and leaves nothing on the Torrents page.
- The Controller owns the deadline. The Grab records when its metadata search started in `metadata_started_at`, and the Controller fails it once the wait has passed since then. A Resolve call carries that deadline, so the Node ends its search at the same time. A Node restart starts a new search with the same deadline.
- A metadata search takes no download slot and no check slot, and ignores held downloads and the disk guard, because it downloads only the info dictionary. Many magnet Grabs search at once.
- A metadata search's announces are outside the announce Ledger, which records only the download's announces.
- A magnet link with no tracker on a Node with DHT off fails at once with `no_peer_source`.
- A metadata search takes no info dictionary larger than `bencode.MaxTorrent`, the 10 MiB cap of an Indexer's .torrent, which also sizes the link's largest message. Once a peer gives a larger size, the Grab fails at Fetching with `torrent_invalid`.
- A Node's DHT runs while its "DHT for public torrents" switch is on and it holds a torrent or a metadata search that `mayDiscover` lets use DHT. Turning DHT on live makes every such torrent announce to the DHT at once.
- A magnet link whose info hash any Torrent row has recorded reuses that row's info dictionary and calls no Node, so the Grabs of a season pack make one search.
- A magnet link doesn't appear on the Torrents page and can't be paused there until its metadata arrives. Its Grab row shows the peers sending metadata and when the search ends.
- The bad-release record of a magnet link that never resolves is its failed Grab, with code `no_metadata` and the magnet link's info hash, because no Torrent exists to carry a fault.
