# A Media Server change is queued per server in the Write that records the bytes

Every library file change becomes a Media Server change for each server whose Path mapping shows its root. The Controller keeps one durable queue per server, as rows of `mediaservers_change`. `files` calls `Changed` inside the Write that records the bytes reaching or leaving their path, so a change commits with the record of its bytes or not at all, and no crash loses one or sends one twice. A new change folds into the open change on its path by the spec's merge table. Two partial unique indexes keep one open change per server and path, and one open Carry per server and file, so a server that is down for a week queues one change per path however often the path changed. Each server has one sender on the Controller. A pass plans the due changes and takes them in one Write, and the server kind's plan merges them by folder: one Plex refresh per folder, or one refresh of the section past 10 folders, and one Jellyfin or Emby report that lists every path. The sender drives each Job with short `Advance` calls that run one step each, and writes the step on the changes after every call. The calls go through the server's Reaching Node. While that Node is offline, the Controller runs the same step itself at the server's Fallback address if its own test of that address passed, and otherwise the changes wait. Decided in [Media Servers](https://github.com/jatassi/SlipStream/issues/160) and its build design. The recorded run of 2026-11-14 on the maintainer's Plex server settled the order of a Plex rename, and the Jellyfin fresh-root run of the same day settled the fresh folder rule.

## Considered Options

- **Event rows, merged when they are sent.** Rejected. A dead server's queue would grow by events until a second merge compacted it. A rename's step would sit on a row that later events keep pointing at, and the Changes tab would list raw events for the web to merge again.
- **Comparing each server with the library's current paths on every pass.** Rejected. It needs no queue, but a rename reads as a removal and an addition. Watch data then has nothing to travel with, an upgrade has no halves to pair, and no row is left to list what a server lost.
- **Queueing after the Write commits, through an event bus or a commit hook.** Rejected. A crash between the commit and the queue's write loses the change. The spec also allows `files` only one injected call.
- **The Controller calling eight primitive operations**, the spec's scan a folder, report paths, look up items, read and write user data, set collections, start a scan and read its state. Rejected. Each product's order would live on the Controller and its wire calls on the Node, and the fallback would need a third copy. One `Advance` call runs one step of the kind's step list on whichever route the pass takes. Workers run the same binary as the Controller (ADR 0003), so shipping the step code to them is safe.
- **The Reaching Node running a whole batch in one call.** Rejected. A Jellyfin or Emby rename waits out two monitor delays of 60 to 90 s each. A dropped link would run the batch again and take a second snapshot, and a Worker holds no durable state to resume from (ADR 0003).
- **Writing watch state and collections back on Plex** through scrobble and the collection routes. Rejected. Plex carries both across a rename that refreshes the destination first (the recorded Plex run, cases B to D), so SlipStream only reports what didn't carry.

## Consequences

- A change is `prepared`, `due`, `sending` or `sent`. `sending` goes back to `due` through the fold when the Controller starts. Nothing else treats `sending` as a lock, because each server has one sender.
- `Changed` wakes the server's sender before its Write commits. SQLite runs one Write at a time, so the sender's next Write starts after that one ends and plans from every change recorded so far. Nothing runs after a commit.
- Steps only move forward, and every step is safe to repeat. A change at a started step no longer folds, so a later change on one of its paths waits behind it. A snapshot is written once, so a retry or a fallback never takes a second one.
- A failure the server responds with counts an attempt and backs the change off. Past "Mark unhealthy after" it makes the server unhealthy for failing sends. A cut link counts nothing. The change goes back to `due` at its step, not before the call's start plus `Timings.Call`. By then the Reaching Node's handler has ended, so the Node and the fallback never both run a step, and a link that drops and returns never reads as a failing server.
- "Wait before sending", 10 s by default, holds new changes until the oldest has waited that long. Either half of an upgrade waits up to `Timings.UpgradePairing` for the other, whatever the wait setting is, so the removal and the addition go as one `replaced` change, and Plex never refreshes a folder with no version in it.
- The fresh folder rule. Before the first change that brings a file into a Fresh folder, the sender looks for an item under the mapping's server folder. If it finds none, it writes when it asked for a full scan and when the last scan before that ended, and only then sends the scan: a Plex section refresh, or `POST /Library/Refresh` on Jellyfin and Emby. The change goes once a scan has ended later than the one before, or once `Timings.ScanEndBound` passes. A retry reads those columns and never starts a second scan. A full scan of an empty folder doesn't make Jellyfin take later reports there (the Jellyfin fresh-root run, case 1), so a removal never starts one, and a mapping counts as scanned only after a scan with a file under it or a found item.
- On Emby the scan has ended when the `RefreshLibrary` task is idle with a later end time, as on Jellyfin. A library's `RefreshStatus` carries no end time, so it can't tell a scan that ended between two looks from one not yet started (the Emby conformance suite).
- Carries keep Watch data. Once per disk queue pass, before a rename's bytes move, `Prepare` snapshots every user's Watch data and the item's collections onto a `prepared` change, within `Timings.RenameSnapshot`. When a server misses that bound, the sender tries the snapshot again at send, while the server may still list the old item. On Jellyfin and Emby a Carry reports the old paths removed, waits for them to go, reports the new paths, waits for the new items, and writes the data and collections back. Emby's API sets no play count or last played, so an Emby Carry lists them as lost.
- A Plex Carry refreshes the destination folders first. It waits up to `Timings.MovedConfirm` for an item at each new path, then refreshes the source folders that no destination shares, then compares the item at each new path with its snapshot. Refreshing the vacated folder first deletes the item and its watch data when Plex empties its trash automatically (the recorded Plex run, case E). Plex keeps no item key across folders, so the item is found again by its new path.
- A Carry whose old path holds no item on the server goes as an added change and loses nothing.
- A Jellyfin change reads as sent one monitor delay after Jellyfin accepts its report. A scan that starts inside that delay drops the pending reports, so the sender reports again once the scan ends.
- A root with no mapping on a server queues nothing for that server. A mapping that a re-home unconfirmed holds its changes until the Admin confirms it. Confirming a mapping, or showing its root, queues a whole library refresh, and the server's acceptance of it marks that library's waiting changes sent.
- Session watching runs only on the Reaching Node and never falls back. The Controller applies a session report only from the server's Reaching Node at the time it applies it, and drops any other with a warning in the log.
