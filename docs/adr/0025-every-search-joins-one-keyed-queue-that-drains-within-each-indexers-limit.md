# Every search joins one keyed queue that drains within each Indexer's limit

Every automatic search goes through one durable queue on the Controller, with one `grabs_due` row per Work and search group. An add, a monitoring or Profile change, a release date, a refresh, a failed Grab, Search all and the Admin's own Search all land on that row, so a group never runs twice at once and a second ask merges into the first. The reconciler starts a run only when every Indexer the run would ask has room. It then dispatches each of the run's lines on its own Indexer, in the Write that reserves the query through `indexers.Reserve`, so an idle Indexer never waits behind a busy one and no query goes past a search limit. A run decides once, after every line has answered, been skipped or gone late, through the one walker that Manual search, RSS sync, wait ends and reruns share. Wants are computed and never stored, so Backlog search keeps the rows in step with the cells, and the other triggers only queue a row sooner. Decided in [Automatic search, Backlog search and RSS sync](https://github.com/jatassi/SlipStream/issues/159) and its build design. On 2026-11-14 the maintainer confirmed that Backlog and bulk lines wait at a limit, and that RSS sync comes first on a tight tracker.

## Considered Options

- **Eager runs, as the spec reads.** Every queued group starts its run at once, and its lines wait for room. Rejected. One tight tracker would hold thousands of open runs, each with its heard Releases, waiting on one window.
- **A durable line per queued group and Indexer.** Rejected. 5,000 groups and 50 Indexers write 250,000 rows per Backlog search run, and the rows go stale whenever an Indexer is turned off or added.
- **Each Indexer's queue built in memory on every pass.** Rejected. Every pass would load the whole queue, and a Read before the Write would let two passes reserve the same slot.
- **Queueing inside the caller's Write by reading cells and search groups there.** Rejected. A bulk change of 500 Works would run grabs' heaviest reads inside the files or library Write, and files would call itself back through grabs.
- **A Backlog line skipping an Indexer at its limit**, as a press does. Rejected by the maintainer. Backlog search would then skip a tight tracker every time its window is full, and could never find what only that tracker lists. The switch would be one case in `indexers.FitOf`, the `ClaimBackground` limit case, and no grabs code would change.
- **Follow-up runs that decide over the Indexers that answered and search the late ones later.** Rejected. A run that decides twice can grab a single beside the pack that a late Indexer lists.
- **The latest trigger takes a merged row**, as the spec says. Rejected. An add or a failure landing on a queued press would put a Hold on the Admin's own search, or drop the gone cells the press asked for.
- **`grabs_search.grab_id`, the spec's link from a run to its Grab.** Rejected. A group run takes several Grabs and joins others, and one column can't hold them.
- **Reserving RSS sync's page cap**, as the spec says. Rejected. On a tracker that allows 50 searches an hour, the 10-page cap leaves Backlog search 2 slots where the pages RSS sync last used leave 11.
- **An uncapped RSS reserve.** Rejected. With a limit of 2 an hour and RSS sync every 15 minutes, the reserve is the whole limit, and Backlog search never searches that tracker's Content Types.
- **`SearchNow` for S40 (Requests and approval)**, as the spec hands off. Rejected. Every owner below grabs asks through `searches.Queue`, so S40 adds a Trigger and a lane like any other caller.

## Consequences

- **Lanes are ranks.** `now` is 10, `bulk` 30 and `backlog` 40, stored as INTEGER in `grabs_nudge`, `grabs_due` and `grabs_search`. `ORDER BY lane` is lane order, and each Indexer's line orders by lane, then run start, then position, so presses lead. The wire carries only the words. Manual search keeps its own runs and starts at once. S40 (Requests and approval) adds rank 20 and its Trigger by rebuilding those three CHECKs in its own grabs migration, and caps the gap of requested Items through `grabs.Config.GapCap`. A queue lane has nothing to do with a Transfer's Lane.
- **One table decides each trigger.** `laneRules` in `internal/grabs/triggers.go` gives each `searches.Trigger` its lane for one Work and for several, and whether it resets the gap, opens gone cells, applies Holds or opens stopped cells. A call with one Ask is one Work. `TestEveryTriggerHasARule` and `TestTriggersMatchTheCheck` keep the table, `searches.Triggers()` and the CHECKs in step.
- **Nudges in the caller's Write.** `searches.Queue` writes one `grabs_nudge` row per Ask and nothing else. It reads no cell and calls no Facet. The nudge commits or rolls back with the change, so a crash can't lose a search, and a Profile Preview's rollback discards its nudge. The reconciler drains nudges into due rows in its own Write, one pass later. The drain always opens its Write, because a Read first can miss a nudge whose Write hasn't committed yet. The press, Search all and Backlog search run in grabs' own Writes and call `enqueue` directly, so the press can answer each group's state.
- **The Admin's press keeps the row.** One entry outranks another when its lane ranks first, or when the lanes tie and only the other's trigger applies Holds. The row takes the outranking entry's trigger and gone cells and keeps its own on a full tie. Its Items are the union, and its queued time is the earlier one. A run takes its row's trigger, so the Searches list names a merged press "Search", and the run reads its Holds from that trigger when it decides. A press whose Items an open run covers promotes that run to the press's lane, trigger and gone cells. The run's planned lines then dispatch as presses, and lines already in flight stay as they are. A trigger that adds Items to an open run queues the group again behind it.
- **indexers alone decides room.** `Reserve(ctx, tx, id, typ, claim)` writes the claim on the `indexers_query` row and answers one of three ways. A query id means the line is sent. A `*WaitError` settles the line with its outcome. A `*RoomError` means the line waits, holding the lines behind it on that Indexer. Searches at once counts true in-flight queries. A background line counts background claims only, and a press counts every claim and may take one slot more. A press at the limit skips `limit_reached`, so a press always gets an answer. A background line at the limit waits. A Busy Indexer whose every in-flight query is past its search wait skips the line `late`, so a stuck site holds neither the queue nor the start rule.
- **RSS sync's reserve.** While RSS sync, the Indexer and its RSS switch are on, `indexers.FitOf` keeps slots from background lines: one per RSS fetch due before the window's oldest reservation leaves, plus the pages the last fetch used (`indexers_rss.last_pages`, at least 1). The reserve is capped at the limit minus 1. On a limit of 50 an hour with 36 used, the oldest leaving in 20 minutes and RSS sync every 15 minutes, the reserve is 3, so 11 background lines may go. Presses ignore the reserve, and RSS sync always comes first on a tight tracker. Only a limit of 1 leaves Backlog search no slot. That Indexer reads Starved, and the hero's popover says "This search waits for TorrentLeech. RSS sync uses all of TorrentLeech's search limit."
- **The lazy start rule bounds open state.** A run starts only when every Indexer it would ask has fewer planned, undispatched lines than its Searches at once, one more for a press (`pace.Room.Starts`). A fast Indexer then runs at most one line ahead of the slowest. Open runs, heard Release rows and line rows stay proportional to the Indexers' Searches at once, whatever the size of the backlog. Backlog search drains a Content Type at its slowest Indexer's pace, and one pass starts at most `StartsPerPass` rows per lane.
- **A paced line waits inside an open run.** The start rule counts only planned lines, so a run can start and then find an Indexer at its limit. Its lines wait inside the run, and the group reads `searching` with `behind` naming the Indexer and when its limit frees a slot. The hero shows `behind` for a searching group as well as a queued one, in its "Why it waits" popover.
- **Expected queries per group.** A run first sends one query per Indexer with the group's terms, or the Item's own terms for a group of one Item. Items that the query left with nothing grabbable at an open cell then get their own query at each Indexer that answered. In the `now` lane, or once the group's gap has reached the longest gap, every such Item does. Otherwise only Items that no automatic run searched before do. `grabs_item_search` holds when an automatic run first searched each Item, and Backlog search's reconcile deletes an Item's row once the Item no longer needs anything, so an Item wanted again gets its own query again. An Item turned off and on again between two Backlog search runs keeps its old row, so it gets its own query only in the `now` lane or once its group's gap reaches the longest gap. A season usually costs one query per Indexer.
- **Backlog search reconciles in chunks.** One Read lists every Work's wanted cells and every due row's key. Writes of at most `BacklogChunk` keys, 500 by default, add, refresh, delete and queue rows, and delete only rows no run took since the Read. A crash between chunks leaves the rest to the next run. A new row's first due time is spread over one interval by its key, so a first run after an import doesn't query every Indexer at once.
- **One walker decides.** `walk` in `internal/grabs/walk.go` hands out Grabs, joins and waits for group runs, RSS sync, wait ends and reruns, through `decideIn`. Manual search's Plan runs the same walk with its pins and without Holds. A `decisionIn` comes only from `runInput`, `rssInput`, `waitInput` or `rerunInput`, and each one sets the scope, which cells open and whether Holds apply.
- **A join table links runs and Grabs.** `grabs_search_grab` holds every Grab a run took (`made = 1`) and every Grab it joined (`made = 0`), RSS runs included. It replaces both `grabs_search.grab_id` and a `grabs_grab.search_id` column. A Grab's `searchId` reads its `made` row, and a rerun reads it to find the run to decide again.
- **The run bound.** A finished run of a group goes once every Item it searched is in a later finished run of the group, no wait holds its Releases and no Grab it made is still fetching. Each Item keeps its latest result, which the read model takes from the latest run, and the Searches list shows each group's latest run. A Grab whose making run was pruned reads `searchId` null and keeps its `foundBy`, which grabs 00015 stores on the Grab (`grabs_grab.found_by`) in the Write that makes it. Each Work keeps only its latest RSS run, and an RSS decision that takes nothing keeps no run.
- **One failure table.** `afterFailure` in `internal/grabs/failures.go` gives each `grabs.Code` what its cells do next, whether it counts toward the stop and whether it refuses the Release for the Work (`tried`). `TestEveryCodeHasAFailureRule` keeps every Code in it. A release fault searches again at once in the `now` lane with trigger `failed_grab`, and that includes a fault found at import, such as `no_video_file`. An Indexer, Node, link or client that is away doesn't search again at once, because the next search would grab the same Release again. Its cells wait for their group's due time. A Grab the Admin picked in Manual search never searches again by itself.
- **The stop is stored.** `grabs_failure.stopped_at` is set on the row whose insert brings a cell's counted failures in the window to "Stop searching again after". The stop outlives the window. The Admin's Search, or Search again on the stopped cell's card, clears the count and the stop and keeps the refusal, and a file that fills the cell deletes its rows. Changing the setting later stops or unstops nothing. Only Backlog search searches a stopped cell, at its pace.
- **When a failed Grab reads Failed.** Its cell reads Failed when the failure needs the Admin and SlipStream isn't searching the cell again: the cell is stopped, the code is a setup fault, the Admin picked the Grab in Manual search, or the code keeps the group's due time. A cell that SlipStream searches again reads Missing or Upgrade, and stays out of the Failed counts.
- **A Controller restart searches once.** A line's deadline is durable, `deadline_at` on its row. The Searching Node keeps a search job and its answer for `JobCap`, 11 minutes, which is longer than the longest search wait of 10. A restarted Controller asks each in-flight line again under the same query id and joins the job. A line past its deadline answers `late` without asking.
- **A Searching Node that drops.** A line asked while no Node can take its query keeps the query in flight and asks again until its deadline, then ends `late`. A Searching Node that restarts, alone or with the Controller, loses its jobs, so a line it hadn't answered searches once more when asked again inside its deadline. The reservation is counted once either way.
- **Reconciling fences search and grab.** While a restored Controller is Reconciling (ADR 0019), dispatch, the deciding Write and its singles, wait ends, Grab now, the press, Search all and the RSS unit's Write do nothing or refuse with `reconciling`. Failure rows, nudges, the drain and Backlog search's reconcile still run, so their searches go once Reconciling ends. The RSS unit ends with the owned skip "Skipped because SlipStream is Reconciling after a restore. RSS sync starts again once Reconciling finishes."
- **RSS sync lives in grabs and matches by title.** The unit's one Write holds grabs' decisions and indexers' feed position, so a crash before it reads the same uploads again, and one info hash never makes two Grabs. No index finds a Work by id, so the library's title search finds candidate Works, the type's clean-title rule decides, and ids only refuse a Work they don't name. The spec had ids find the Work first. A Grab made when an RSS wait ends records the source `search` and `foundBy` `search`, because the wait builds its run without a trigger.
